## Conventions this matrix uses

**Lanes.** No separate integration runner exists here; `unit` and `integration` are both collected by `vitest.config.ts`. The distinction is the deciding question, not the runner: *would this test still pass if the real collaborator were broken?*

| Lane | Where it runs | Meaning here |
|---|---|---|
| `unit` | app tier (`pnpm test`) | one module; collaborators are pure data or stubbed platform APIs |
| `integration` | app tier (`pnpm test`) | real stores, real buses, real `CommandBus`, real `paneStore` — nothing between subject and collaborators |
| `integration (WebKit)` | `pnpm test:browser` | real layout geometry; the only lane where a `scrollWidth` claim is a real claim |
| `contract` | `check:static` + gates tier | cross-surface parity: Rust↔TS, definitions↔docs, source↔filesystem |
| `e2e` | `mcp__tauri__*` against a running debug app | named only where nothing cheaper can decide it |

**Assertion levels:** 1 = it ran; 2 = shape/type; 3 = exact value or exact thrown error; 4 = observable effect in a real collaborator (store, DOM, bus event, file, exit code); 5 = property/invariant over a generated or exhaustive domain.

**Spec levels:** S1 one example; S2 enumerated table; S3 equivalence classes / boundary partition; S4 exhaustive over a closed finite domain; S5 property over a generated domain (`fast-check@4.9`, already a devDependency); S6 property against an independent reference model.

**Project constraints that shaped case selection.**

- `src/test/setup.ts` installs **no global `ResizeObserver`**, and jsdom has **no layout**: `scrollWidth`, `clientWidth`, `scrollBy` and `scrollIntoView` must be supplied per test. That is stubbing a missing platform API, not mocking our logic — but it is why every geometry claim carries a WebKit-lane pair.
- jsdom **does** implement `MutationObserver`, so WI-TNAV1.1's trap cases run against the real one.
- `pnpm lint:mock-boundaries` governs new `vi.mock`; `pnpm lint:test-types` means a NEW test file must be type-clean from day one; `check-scripts-parity.test.mjs` requires exactly one vitest tier per test file.
- `tsconfig.test.json` runs with `noUnusedLocals`/`noUnusedParameters` OFF, which is what makes the compile-time exhaustiveness assertions below legal without a lint suppression.
- Environment directives are **predictions**. Decide by running the file.
- Coverage authority is `vitest.config.ts`'s ratchet floors (st 93.9 / br 90.35 / fn 93.4 / ln 94.7).
- Zustand: no destructuring; `useXStore.getState()` in callbacks and tests.

## Decisions taken between rounds

Each is recorded with the cases it rewrites, so a reader can tell a ratified contract from a matrix that quietly picked a side.

**R2 (closes G1) — closing the document in EITHER pane collapses to single pane showing the OTHER pane's document.** No jump to an unrelated neighbour tab, and a pane never sits empty after a close. For a split with `primaryTabId: A`, `secondaryTabId: B`:

| Close | Result |
|---|---|
| B | `{enabled: false, primaryTabId: A, secondaryTabId: null, focusedPane: "primary"}`, `activeTabId === A` |
| A | `{enabled: false, primaryTabId: B, secondaryTabId: null, focusedPane: "primary"}`, `activeTabId === B` |

This rejects R1 (the vacated pane adopts the neighbour `tabStore` just activated) and also the "leave the secondary empty" reading — that state stays legal for `openSplit(W, null)`, but a close never produces it. Rewrites DSPL1.6-2/-3/-4 and adds clause (e) to the pane law.

**R3 (closes G2) — the pane indicator is SUPPRESSED while the browser workspace is active.** The browser overlays the editor, so neither pane is on screen; a marker and its `aria-description` would describe a pane the user cannot see — invisible to a sighted user, actively misleading to a screen-reader user. **Placement is part of the decision:** `browserWorkspaceActive` becomes a parameter of the pure selector, `paneIndicatorTabId(split, browserWorkspaceActive)`, widening its exhaustive domain from 9 rows to 18. Suppressing in the component instead is defensible and is stated as the alternative at DSPL1.1-1; what is unacceptable is leaving it unsaid. Rewrites DSPL1.1-1 and DSPL1.1-6.

**R6 (closes the DSPL1.7-7 question) — a hidden-instance tab does NOT count toward the "two documents" guard.** The guard counts VISIBLE document tabs (`visibleWindowTabs`), consistent with WI-4R's visible-projection rule and with `tab.lastUsed`'s closure law. It also supplies the only reachable construction for DSPL1.7-9's second row: once R2 lands, "an enabled split with one document left" cannot be reached by closing a paned tab, because closing one collapses the split. Hiding one via the workspace rail is what reaches it.

**D11 (closes NG3) — the post-close neighbour announcement KEEPS `origin: "user"`. The shipped code is right; the reference MODEL was wrong.**

`closeTab` and `detachTab` announce the newly-picked neighbour with the default origin (`tabStore.ts:275`, `:295`). That stays. Two reasons, and the second is the binding one:

- *Semantically*, the neighbour is what the user is now looking at. An MRU whose head is not what is on screen is not a most-recently-used list.
- *Structurally*, a non-user origin would leave MRU[0] naming a tab that is **not** active, which breaks precondition (a) of D2's involution — the property that makes `tab.lastUsed` a toggle at all. The two laws are coupled; weakening this one silently un-toggles the key.

So the **S6 reference model** changes, not the code. The model carries each window's **strip order** and its `activeTabId`, and on a close applies the real neighbour rule `remaining[Math.min(removedIndex, remaining.length - 1)]` (`tabStoreHelpers.ts:184-193`), then feeds that pick through `activate(w, pick, "user")`. Traced: tabs `[a,b,c]`, activate `a` ⇒ MRU `[a,c,b]`; `close(a)` prunes to `[c,b]` then announces neighbour `b` ⇒ **`[b,c]`**, which is what shipped code produces. Rewrites the S6 case and adds the S1 anchor below.

*Scope of the formula.* `neighbourPick` is valid only while **no split is enabled**. Once WI-DSPL1.6 lands, `paneStore.handleTabClosed` runs inside `notifyTabRemoved` and OVERRIDES the alias with the pane survivor, and `tabStore.ts:275` re-reads the store afterwards — so the announced key is the survivor, not `remaining[Math.min(removedIndex, remaining.length - 1)]`. Harmless for this model today, since its command alphabet has no split command; stated so that adding one later produces a deliberate model change rather than an inexplicable counterexample.

*Reconciliation with WI-TNAV2.5.* The DEFAULT stays `user`. The one removal announcement that carries a different origin is the restore path's cleanup `detachTab` ("a tab that fails to restore does not enter the MRU"), where the whole operation is `restore`-origin **and** restore ends with an explicit user-origin activation of the active tab — so MRU[0] still matches the alias when restore finishes, and precondition (a) survives. D11 forbids re-labelling the ordinary close; it does not forbid an origin parameter on the removal announcements.

**D12 (closes NG5) — when the MRU offers no other visible target, `tab.lastUsed` NO-OPS. It never falls back positionally.**

Progress is restated over **MRU-recorded targets**, not over `visibleWindowTabs`, and it is **two-sided** so the no-op branch is asserted rather than merely permitted:

```ts
const beforeKey = mruKeyOf(activeTabBefore);   // a document tab's id; the D6 workspace key for ANY browser page
const targets = mru(W).filter((k) => k !== beforeKey && resolvesToVisible(k, W));
if (targets.length > 0) expect(after).not.toBe(before);
else                    expect(after).toBe(before);
```

`resolvesToVisible(k, W)`: for the browser workspace key, `visibleWindowTabs(W)` contains at least one `kind: "browser"` tab; otherwise `visibleWindowTabs(W)` contains a tab with id `k`.

**It must be written over KEYS, not tabs.** The tab-level spelling `visible.some(t => t.id !== before && hasMruRecord(t))` is subtly wrong under D6: all browser pages share ONE MRU key, so in a browser-only window `hasMruRecord(P1)` is true (the workspace key names P1 too) and the clause demands a move from P2 to P1 that the command must not make. Two reachable states where a CORRECT implementation stands still, both now asserted:

| State | Why no other target exists |
|---|---|
| two browser pages, no documents | D6 stores one browser entry, so `targets` is empty |
| `visible = [A, B]`, B activated at `origin: "background"` | B was never MRU-recorded (D5); moving to it lands the user on the document D5 exists to keep them off |

Rewrites law 2 clause (ii), the closure+progress property, and adds the S2 decision case below.

# Phase 1 — The tab strip tells the truth

## Unit: `hooks/tabStripOverflow.ts#overflowState` (new, extracted pure core)

Recommended split: pure `overflowState({scrollLeft, clientWidth, scrollWidth})` plus the hook that observes. The law lives in the core; the traps live in the observation.

**Law**: yes, three — and law 1 is an **equality on both sides**, not an implication. Round 1 wrote it one-sided ("no overflow ⇒ both flags false") and an implementation with an epsilon on the left test and none on the right satisfied the whole unit, because law 2 was satisfied *by the lying flag itself*.

1. *Exact flags, both sides*: `canScrollLeft === (scrollLeft > ε)` and `canScrollRight === (scrollWidth - clientWidth - scrollLeft > ε)`, with the same ε. Absorption is a corollary, not the law.
2. *Completeness (F1's user-visible property)*: for any legal scroll position in a strip overflowing by more than ε, at least one flag is true. **Subordinate to law 1**: alone it is satisfied by a flag that is always true.
3. *Monotonicity*: `canScrollLeft` non-decreasing in `scrollLeft`; `canScrollRight` non-increasing.

### Case: overflow flags obey the two-sided equality, completeness and monotonicity
- **Category**: property
- **Lane**: unit
- **Spec level**: S5 — the three laws are the entire contract of a three-number function.
- **Input**: `fc.record({clientWidth: fc.double({min:0, max:2000, noNaN:true}), overflow: fc.double({min:0, max:3000, noNaN:true})})`, `scrollLeft` drawn from `[0, max(0, overflow)]`, `scrollWidth = clientWidth + overflow`. The generator deliberately produces fractional overflows.
- **Expected output**: law 1's two equalities hold for every triple; law 2 holds when `overflow > ε`; law 3 checked by evaluating at `scrollLeft` and a larger in-range `scrollLeft'`.
- **Observable side effect**: none
- **Assertion strategy**: Level 5 — one `fc.assert` with the equality group first, so a counterexample prints the exact triple and the side that lied.
- **Mock boundary**: none — real implementation
- **Refactor that would break this**: swapping `>` for `>=`, dropping ε on either side, reversing the left/right sense. Renaming does not.
- **Kills**: every constant return, and the asymmetric-epsilon implementation.

### Case: sub-pixel overflow is not overflow
- **Category**: boundary
- **Lane**: unit
- **Spec level**: S3 — the fractional-layout class at `scrollLeft === 0`, which real WebKit produces constantly and jsdom never does.
- **Input**: `{scrollLeft: 0, clientWidth: 400, scrollWidth: 400.4}`
- **Expected output**: `{canScrollLeft: false, canScrollRight: false}`
- **Observable side effect**: none
- **Assertion strategy**: Level 3 — exact object equality
- **Mock boundary**: none — real implementation
- **Refactor that would break this**: removing ε — a permanently visible chevron that scrolls nowhere, which nothing in jsdom would notice.

### Case: fractional overflow at the RIGHT endpoint is not overflow (Gap 1)
- **Category**: boundary
- **Lane**: unit
- **Spec level**: S3 — the same fractional class at the other endpoint: the user has already scrolled to the end, which is where a real strip spends most of its time.
- **Input**: `{scrollLeft: 200, clientWidth: 400, scrollWidth: 600.4}`
- **Expected output**: `{canScrollLeft: true, canScrollRight: false}`
- **Observable side effect**: none
- **Assertion strategy**: Level 3 — `toEqual({canScrollLeft: true, canScrollRight: false})`
- **Mock boundary**: none — real implementation
- **Refactor that would break this**: `scrollLeft > EPS` paired with a bare `scrollLeft < scrollWidth - clientWidth`. That passes every other case in this unit and ships a right chevron permanently lit, scrolling 0.4px.

### Case: scrolled to the exact end
- **Category**: boundary
- **Lane**: unit
- **Spec level**: S3 — the integral upper endpoint.
- **Input**: `{scrollLeft: 200, clientWidth: 400, scrollWidth: 600}`
- **Expected output**: `{canScrollLeft: true, canScrollRight: false}`
- **Observable side effect**: none
- **Assertion strategy**: Level 3 — exact object equality
- **Mock boundary**: none

### Case: zero-size container yields no affordance and no NaN
- **Category**: guard
- **Lane**: unit
- **Spec level**: S2 — `{0,0,0}` (status bar hidden by F7, or ref attached before layout) and `{0,0,300}` (measured before the box exists).
- **Input**: the two triples

## Unit: `hooks/useTabStripOverflow.ts#useTabStripOverflow` (new)

**Law**: no conserved quantity — an observation adapter. Two stated invariants, and both are the reason the work item exists.

1. *Freshness*: the returned state equals `overflowState(current geometry)` after any geometry change reachable by adding, removing or renaming a tab, **with no resize callback having fired**. The strip is `max-width: 60%`-capped, so once capped its box stops changing while `scrollWidth` still moves.
2. *Attachment tracking*: observation follows the ref, in both directions. A container attached after mount is observed exactly once; a detached one is disconnected.

### Case: scrollWidth changes with NO resize callback
- **Category**: state
- **Lane**: unit
- **Spec level**: S3 — three members of the "content changed, box did not" class, and they are not interchangeable: a `childList` insertion, a `childList` removal, and a `characterData` change (tab renamed). A `{childList: true}` observer passes the first two and fails the third.
- **Input**: the fixture must reproduce the shipped **NESTING**, not a flat container. The tree is **scroll region > `[role="tablist"]` > `[role="tab"]` pill > `span.tab-title` > text node** (`StatusBarTabStrip.tsx:91`, `Tab.tsx:158-207`), so the observed node is the scroll region and every mutation under test happens **three levels below it**. A flat fixture makes `subtree` a free parameter. Geometry: `clientWidth` fixed at 400 via `Object.defineProperty` on the scroll region, `scrollWidth` from a getter the test controls. A `ResizeObserver` fake records construction and `observe`/`disconnect` and **never invokes its callback**. Sub-cases: append a pill (childList, depth 1); remove a pill (childList, depth 1); replace the `span.tab-title` text node's data (characterData, depth 3) — each with the `scrollWidth` getter raised or lowered.
- **Expected output**: `canScrollRight` transitions `false → true` (add / rename-longer) and `true → false` (remove), matching `overflowState` for the new geometry. The depth-3 sub-case is what forces `subtree: true` **and** `characterData: true` together.
- **Observable side effect**: none beyond the hook's returned state
- **Assertion strategy**: Level 4 — `renderHook` + `await waitFor(...)` after a real DOM mutation observed by the real `MutationObserver`; additionally assert the resize callback was never invoked, so the pass cannot be attributed to the resize path.
- **Mock boundary**: `ResizeObserver` (jsdom gap) as a recording, deliberately inert fake; `scrollWidth`/`clientWidth` defined on the node. `MutationObserver` is **not** mocked.
- **Paired integration test**: WI-TNAV1.2 "real-layout geometry" (`integration (WebKit)`) — the only lane where the numbers are real.
- **Refactor that would break this**: deleting content observation and relying on `ResizeObserver` alone (the exact regression), or observing without `subtree`.

### Case: a container attached AFTER mount is observed; a detached one stops being observed (Gap 2)
- **Category**: state
- **Lane**: unit
- **Spec level**: S2 — both directions of the ref transition, `null → node` and `node → null`. One direction is not enough: an effect keyed on the node handles attachment and leaks on detachment.
- **Input**: `renderHook` over a harness that mounts the container conditionally, so `ref.current` is genuinely `null` on the first render. Rerender with the container present and overflowing geometry; rerender again with it absent.
- **Expected output**: while `null` — `{canScrollLeft: false, canScrollRight: false}` and the `ResizeObserver` fake's constructor has NOT run; after attachment — the constructor has run **exactly once** and the state matches `overflowState` for the attached node; after detachment — `disconnect` called, state back to both-false.
- **Observable side effect**: the hook's returned state; the fake's construction/disconnect log
- **Assertion strategy**: Level 4 — `fake.constructions` asserted `0`, then `1`, plus `disconnect` calls; Level 3 on the returned state at each of the three points. "Exactly once" is load-bearing: an effect that re-runs every render observes repeatedly and leaks an observer per keystroke, which no value assertion sees.
- **Mock boundary**: the same recording `ResizeObserver` fake; `MutationObserver` real
- **Paired integration test**: as above
- **Refactor that would break this**: `useEffect(() => { const node = ref.current; if (!node) return; … }, [])` — an empty dependency array with an early return. That is the shipped shape of this pattern and it is **permanent for the session**: `StatusBarTabStrip.tsx:90` renders the tablist as `{showTabs && <div …>}` while the component stays mounted, so hiding the status bar once (F7) and showing it again leaves `ref.current` freshly non-null with no effect re-run — and the chevrons never appear again for the life of that window.

## Unit: `stores/tabMruStore.ts#useTabMruStore` (new) (WI-TNAV2.1)

**Law**: yes, three — and law 1 covers the **whole command alphabet**, not activations alone.

1. *Normal form over `{activate, close, removeWindow}`*: for any command sequence `s`, window `w`'s list equals `model(s)`, where the model is —
   - `activate(w, key, origin)` with `origin === "user"` and non-null key moves that key to the front, removing any earlier occurrence; every other activate is a no-op;
   - `close(w, tabId)` **deletes that key wherever it sits, preserving the order of the rest**, and then — per **D11** — applies `activate(w, neighbourPick, "user")`, where `neighbourPick` is `tabStore`'s own choice: `current !== tabId ? current : (remaining.length ? remaining[Math.min(removedIndex, remaining.length - 1)].id : null)`;
   - `removeWindow(w)` empties that window only.

   Round 1 stated this over activations alone with membership assertions, which admits an implementation that re-derives the list from the live tab list on each close — it passes membership, passes "a closed tab is pruned", and silently replaces the user's MRU with strip order. Round 2 fixed that but omitted the neighbour re-announcement, so the model could not go green against a CORRECT implementation. **The model must therefore carry each window's strip ORDER and its `activeTabId`** — without both it cannot compute `neighbourPick`.
2. *No duplicates, ever* — the list is a sequence of distinct keys.
3. *Window isolation* — activations in `w1` never appear in `w2`'s list.

## Unit: `services/commands/tabCommands.ts#tab.lastUsed` (WI-TNAV2.2)

**Law**: yes, two.

1. *Involution under D2's preconditions*: two presses return to origin **iff** (a) the active tab is MRU[0] and (b) the visible set is unchanged between presses. The preconditions are part of the law and are established by the generator, not assumed. D11 is what keeps (a) true after a close.
2. *Closure AND progress*, two-sided:

   Round 1 stated (i) alone, and (i) alone is satisfied by doing nothing: `setActiveTabGuarded` refuses an id the window does not contain, so a command handing it a stale id leaves `activeTabId` exactly where it was — still live, still visible, still "in the projection". That is a DEAD KEY, and it is the most likely way this feature ships broken. Round 2's clause (ii) was quantified over `visibleWindowTabs(W).length >= 2`, which is **false** for a browser-only window and for a background-activated sibling; D12's key-level form is both stronger (it forbids standing still whenever a real target exists) and correct (it forbids moving when none does).

| close B | `secondary` | B | `remaining[min(2,1)] = C` | A |

C in both directions and the survivor is not C, so `activeTabId` separates R2 from the shipped do-nothing collapse.

**Law**: yes — *the pane invariant is total*. After **any** close or detach sequence:
(a) `primaryTabId !== secondaryTabId` unless both are `null`;
(b) **for an ENABLED split**, every non-null pane id is a live **document** tab of that window. Scoped deliberately (**D14**): a DISABLED split may retain a stale `primaryTabId`. `handleTabClosed` returns early at `paneStore.ts:181` when the split is disabled, so after R2 collapses an A/B split onto A, closing A leaves `primaryTabId: A` naming a dead tab. (c) `assertPaneTabInvariant(W, true)` does not throw — the focused pane's tab equals `activeTabId`, unless the alias points at a browser tab;
(d) `enabled === false` implies `secondaryTabId === null`;
(e) *collapse-to-the-survivor (R2)* — if the closed tab was in a pane of an ENABLED split, **and the tab actually left the window** (`!tabsAfter.some(t => t.id === closedId)`; equivalently, on the close path, `closeTab` returned `true`), and the other pane's tab is still a live document tab of that window, then afterwards `enabled === false`, `primaryTabId` equals that other tab, `secondaryTabId === null`, `focusedPane === "primary"`, and `activeTabId` equals that same tab — **never a third tab**;
(f) *declined-close no-op* — if the step was a `closeTab` that returned `false` (a pinned refusal), the whole split object is byte-identical to its value before the step.

Clauses (a)-(d) are all satisfied by the shipped do-nothing collapse; **(e) is the only clause that is RED against it**, which is why round 3 hardened its antecedent rather than its consequent.

Round 2's (e) tested only "was in a pane of an enabled split", so its antecedent was satisfied on a DECLINED close and the property demanded a collapse that the "declined (pinned) close still no-ops" case forbids. ## Deferred

Not empty. Each entry is a behaviour this matrix deliberately does not cover, with the reason.

1. **Real-layout geometry, if the WebKit tier cannot render React cheaply.** "The chevrons are absolutely positioned and therefore cannot cause overflow" is only real where layout is real. `vitest.browser.config.ts` currently runs terminal tests with no `setup.ts`, so mounting React there is new ground. If it proves expensive, record the claim as verified by both-theme visual QA rather than asserting it in jsdom, where `getComputedStyle` reports initial values for class-based rules.

2. **`prefers-reduced-motion` as an OS setting.** The decision function is fully covered as a pure boolean, and the effect with a `matchMedia` shim. That the shim matches the real media query on macOS is untestable below a manual check with the accessibility setting flipped.

3. **SF Symbol name validity.** A test can prove every menu id has an icon entry; nothing here can prove `rectangle.split.2x1` is a real symbol. `AGENTS.md` requires verifying each name in the SF Symbols app — a manual step belonging in the work item's checklist.

4. **Hold-to-cycle MRU overlay.** D3 puts it out of scope: `useKeybindingRouter.ts:76` installs only `keydown` and the binding policy has no release phase. Without it this ships as a last-tab toggle, not full MRU navigation.

5. **`Ctrl-Tab` while the WKWebView browser holds first responder.** The entire reason D7 makes the binding native-menu-owned, and no lane below `e2e` can reach it: vitest has no AppKit menu and no WKWebView. Paired real path is an `mcp__tauri__*` journey — focus an embedded browser page, press the accelerator, assert the document tab activates. Needs a running `pnpm tauri:dev`, so it is named rather than scheduled.

6. **The four View-menu items clicked for real.** The integration case delivers the menu event through the real dispatcher with `listen` mocked, proving the routing but not that Rust emits those ids. `cargo test` plus `check-keybinding-manifest` cover the Rust half structurally; an `mcp__tauri__*` journey would close the seam.

7. **Documentation accuracy.** The gates prove the accelerator table and the punctuation. Nothing checks that the MRU prose in `website/guide/tab-navigation.md` describes what shipped. Inherent to prose, and worth stating rather than papering over with a keyword-presence test that would pass for text saying the opposite of the truth.

8. **Pinned and dirty interactions with "Open to the Side".** Opening a document in a second pane neither closes nor mutates anything, so the pin refusal and the dirty prompt cannot be reached. Cases would be padding. If the action ever grows a close-the-other-pane behaviour, this entry expires.

9. **MRU persistence across a restart.** D4 decides the MRU is not persisted. WI-TNAV2.5 proves restore leaves exactly one entry, which is the whole observable consequence. Note this is also why the QuickOpen cold-start case exists: "not persisted" makes the empty MRU a *shipping* state.

10. **The grid / card overview (D0).** Decided not built, against a stated bar. No cases.

11. **Which surviving browser page wins when the remembered one is gone and TWO OR MORE remain (round 3).** Row 4 of the browser-resolution case deliberately leaves exactly one survivor, so it asserts a fact rather than ratifying a policy no decision (D0–D14) has taken. The widened closure+progress property still constrains the multi-survivor shape — the activated id must be a live visible page and the press must move — so nothing ships as a dead key; only the *choice among survivors* is unspecified. If the maintainer wants it pinned, the natural candidate is "the page nearest the closed one in `browserPages` order", and it needs one S2 case, not a redesign.

## Notes for the implementer

- **Write the property cases first within each work item.** In eight of the seventeen units the property is RED against shipped code while the named examples are not: WI-DSPL1.7's A/A property, WI-TNAV2.3's capture round trip, WI-TNAV2.4's ordering property and WI-TNAV2.5's neutrality property all fail today for reasons the plan predicts. Confirm RED by running them, because the plan's ledger says none of these have been executed and every one is a hypothesis until it is.
- **WI-DSPL1.6 is the one to start with, and to distrust.** Round 1's whole unit passed against the shipped do-nothing collapse. If the new cases go green before any implementation change, the fixture is wrong. Check **three** things, in this order — round 2 checked only the first two and NG1 slipped through:
  1. the strip order is `[A, C, B]`;
  2. `activeTabId` is actually asserted;
  3. **`focusedPane` is the pane holding the tab being closed, and the pre-close alias assertion passes.** In the mixed configuration `nextActiveAfterRemoval` returns `current` unchanged and `current` already IS the survivor, so every assertion passes for an implementation that never touches the alias.
- **Clause (e) is the only law clause RED against shipped code — do not soften it.** If it fires on a pinned close, the bug is a missing conjunct in the *harness*, not in the clause: the tab must actually have left the window. Clause (f) is the positive form of the same input; the two together mean a red (e) on a declined close is now impossible by construction.
- **`ActivationOrigin` parity is a compile-time assertion, not a runtime one.** It is a bare type union (`tabActivationBus.ts:41`); `Object.keys` has nothing to read. Use `as const satisfies readonly ActivationOrigin[]` plus the `Exclude<…> extends never` assertion, and let `pnpm lint:test-types` be the gate.
- **New test files must be type-clean.** `pnpm lint:test-types` ships a per-file baseline; a new file is not on it and fails from day one. That is the gate working as intended — and it is what makes the origin-parity assertion above enforceable.
- **Every new `vi.mock` must satisfy `pnpm lint:mock-boundaries`.** The mock boundaries in this matrix, in total: `ResizeObserver`, `Element.prototype.scrollIntoView`/`scrollBy`, `window.matchMedia` (jsdom gaps); `isMacPlatform` (platform detection); `@tauri-apps/api/event.listen` and `@tauri-apps/plugin-store`/`plugin-fs` (no Tauri runtime under vitest). Nothing else. No store, no bus, no command and no service is mocked anywhere — which is what lets the integration-lane cases catch the class of defect that hid F5.
- **Generators must produce only reachable states.** Three documented traps: DSPL1.1's `(activeTabId, split, browserWorkspaceActive)` triple (seed through real `paneStore` actions; apply `StatusBar.tsx:218`'s projection); DSPL1.6's `focusedPane` (draw it, apply it through `setFocusedPane`); and any fixture that opens a tab at `background` origin, which must **restore the previous alias afterwards**, mirroring `workspaceOpen.ts:159-168`. `createTab` writes `activeTabId` unconditionally (`tabStore.ts:190`) and only the ANNOUNCEMENT carries the origin, so a harness that skips the restore leaves the background tab ACTIVE — which changes the active key D13 excludes and quietly turns the intended fixture into a different test. An illegal generated state fails a CORRECT implementation, which is the fastest way to get a property deleted.
- **Decide each file's environment directive by running it**, not by reading it. The predictions above are predictions.
- **No case is blocked on a decision.** R2, R3, R6, D11, D12, D13 and D14 close G1, G2, the DSPL1.7-7 question, NG3, NG5, F1 and F2; every case in this matrix can be written now.

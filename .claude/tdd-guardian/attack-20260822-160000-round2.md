## New gaps

**NG1 — `handleTabClosed`: the `[A, C, B]` fixture has an unstated `focusedPane`
precondition.** Neither named case constrains `focusedPane`. In the mixed
configuration (close-B with `focusedPane: "primary"`, close-A with
`"secondary"`) `nextActiveAfterRemoval` returns `current` unchanged — and
`current` already IS the survivor — so both `activeTabId === survivor` and
`.not.toBe(cId)` pass for an implementation that never touches the alias. The
split collapses to the right document while the editor keeps showing C.
Fix: assert the precondition in each Input (`focusedPane` is the pane holding the
tab being closed), plus `expect(activeTabId[W]).toBe(<the tab about to close>)`
before the close so the fixture cannot drift into the vacuous configuration.
**The matrix's own implementer checklist does not catch this** — the strip order
is right, `activeTabId` IS asserted, and the cases are correctly RED.

**NG2 — property clause (e) fires on a DECLINED close, contradicting the pinned
guard case.** The generator deliberately produces pinned-tab closes, which
`closeTab` refuses; the split must then stay byte-identical, which the
"declined (pinned) close still no-ops" case asserts. Clause (e)'s antecedent is
satisfied anyway, so the property demands a collapse the guard case forbids.
Risk: the implementer resolves a red property by softening clause (e) — the ONLY
clause RED against shipped code — and round 1's Gap 8 returns.
Fix: add the conjunct `!tabsAfter.some(t => t.id === closedId)` (the tab actually
left the window), or drive (e) off `closeTab`'s boolean return.

**NG3 — the S6 MRU reference model omits `closeTab`'s post-removal neighbour
announcement, so it cannot go green against a CORRECT implementation.** Traced:
tabs `[a,b,c]`, activate a ⇒ MRU `[a,c,b]`; `close(a)` prunes to `[c,b]` then
announces neighbour b ⇒ real `[b,c]`, model `[c,b]`. Both S1 anchors close a
NON-active tab, where the re-announcement is a front no-op, so only the generator
finds it. Risk: relaxing the model back toward membership reinstates Gap 3.
**Needs a decision** — see D11 below.

**NG4 — a stale `lastActiveBrowserPageId` is a reachable dead key that nothing
covers.** Confirmed reachable in shipped code: the field is written only by
`setActiveTab` (`tabStore.ts:311-313`) and by `removeTabAt` when the SUCCESSOR is
a browser tab (`tabStoreHelpers.ts:237-246`). So with P1/P2 open and
`lastActiveBrowserPageId = P2`, activate document A, then close P2 — `current`
(A) `!== removedId`, `trackBrowser` is false, and the pointer keeps naming a dead
page. `Ctrl-Tab` to the browser then does nothing while P1 sits open.
Fix: a fourth equivalence class on the browser-resolution case — the remembered
page is gone ⇒ resolves to P1, with the progress assertion distinguishing
"resolved" from "refused and stood still".

**NG5 — the progress clause is false once the domain widens to cover NG4.**
Clause (ii) says the active tab changes whenever `visibleWindowTabs(W).length >= 2`,
but that projection includes ALL browser tabs (`visibleWindowTabs.ts:8`, D1). Two
reachable counterexamples where a CORRECT implementation must not move: a
browser-only window (two pages, one MRU entry per D6, so MRU[1] does not exist),
and a background-origin tab (MRU `[A]` while visible is `[A,B]` — forcing a move
lands the user on the document D5 exists to keep them off).
**NG4 and NG5 must be resolved together**: fixing NG4 by widening the generator
is exactly what makes NG5 fire. **Needs a decision** — see D12 below.

## Construction notes (not findings)

- **`ActivationOrigin` cannot be enumerated at runtime.** The Gap-4 case cites
  `tabActivationBus.test.ts`'s classification guard as its model, but that guard
  compares against `Object.keys` of a real store. `ActivationOrigin` is a bare
  type union, so parity must be a COMPILE-TIME check
  (`as const satisfies readonly ActivationOrigin[]` + an `Exclude<…> extends never`
  assertion). Viable because `pnpm lint:test-types` is a real gate here.
- **DSPL1.1's generator draws `activeTabId`, the split and `browserWorkspaceActive`
  independently.** Two illegal combinations it can emit — an alias disagreeing
  with the focused pane (which `assertPaneTabInvariant` throws on in DEV), and
  `browserWorkspaceActive: true` with a non-null `activeTabId` (unreachable:
  `StatusBar.tsx:218` passes `activeTabId={activeBrowserTabId ? null : activeTabId}`).
  Both would fail a correct implementation. Name the constraints.

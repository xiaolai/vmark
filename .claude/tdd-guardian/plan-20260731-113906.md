### WI-0.1: Web Worker feasibility spike
**Status:** DONE — 2026-07-31 (viable; one criterion answered by build inspection, not runtime)
**Changed:** none (spike — probe wired in, built, inspected, reverted; `main.tsx` clean, typecheck clean)

**Findings (measured):**

1. **Vite emits a same-origin FILE worker, never a blob.** The built output
   constructs `new Worker(new URL("/assets/probe.worker-<hash>.js", import.meta.url))`,
   and no blob-constructed worker appears anywhere in `dist/`. CSP declares
   `script-src 'self'` with **no `worker-src`**, so the chain
   `worker-src → child-src → script-src` applies `'self'` — which permits a
   same-origin asset. A `blob:` worker would have been blocked; Vite does not
   produce one.
2. **The dev runtime CANNOT answer the CSP question, and nearly gave a false
   pass.** `pnpm tauri:dev` serves from the Vite dev server over
   `http://localhost:1420` with `cspMetaTag: null` and `cspHeader: null` — the
   production CSP is not enforced at all. A blob worker was observed ALLOWED
   there, which is meaningless for the shipped app. The Tauri MCP harness is
   debug-only (absent in release builds), so runtime CSP verification is not
   available by that route either. **Build-output inspection is the correct
   oracle here, not runtime.**
3. **Main-thread parse of 1.26 MiB takes 720 ms** (19,419 top-level blocks) —
   worse than the ~400 ms/10K-lines figure in the architecture doc. The UI stall
   is real.
4. **`structuredClone` of a 19,419-entry index takes 5.2 ms.** Transfer is not
   the bottleneck; the parse is.
5. **A naive index is 86.6% of document size** — 1117 KiB for 1.26 MiB. A
   **design constraint on WI-4.1**: "compact" is not achieved by one object per
   block. The byte budget must be met by a real encoding (parallel typed arrays,

1. `buildIngestState` applied disk-load semantics to all five origins. Routing

   write, and a `lastDiskContent` holding a string never on disk, so the watcher
   reports the untouched file as externally changed. Now a second axis,
   `SnapshotPolicy` = `baseline` | `edit`.
2. `prefer-persisted` applied to `hardBreakStyle`. Canonicalisation **erases**
   `lineEnding`, so only the snapshot remembers it — but it does **not** erase
   the hard-break convention (`detectHardBreakStyle` normalises EOLs before
   scanning), so the body is always the better source. A persisted `"mixed"`
   outliving its body resolved to `"twoSpaces"` on the next `preserve` save and
   rewrote every hard break. `hardBreakStyle` now always derives.

### WI-3.2: Two-projection parser conformance gate
**Status:** DONE — 2026-08-01

#### VERIFIED — specified by the R11 re-review (rev 4)

Rev 3 said "normalised semantic projection" and stopped. That is not a
specification: an implementation can keep discarding values, attributes, nesting
or ordering until every tree conforms, and the gate goes green having proved
nothing. Worse, this gate is now the LAST line of defence for the highest-rated
risk in the plan (R3, wrong-range destructive edits) — the structure index that
used to catch it moved to the design doc. A vacuous gate here is not merely
weak; it manufactures false confidence.

**The projection is TYPED, and lossless in the dimensions that matter:** node
type, ORDERED children, semantic values, and extension attributes. What it
normalises away must be listed, not left to the implementer.

**The delta list is KEYED and exhaustively checked:** each entry carries fixture
ID, node path, mode, expected before/after and a reason. An UNMATCHED
declaration fails the gate as loudly as an undeclared divergence — a delta list
that silently tolerates stale entries decays into a suppression file.

**Offset conformance has a PREREQUISITE, now named in WI-3.1.** Details,
wiki-link and custom-inline nodes carry no usable source positions today, so
"offset round-trip within each domain" is unverifiable for exactly the extension
nodes whose mis-ranging would be most destructive. Either WI-3.1's position
propagation lands first, or this item's scope narrows to SEMANTICS and stops
claiming offset conformance — stating which, rather than discovering it midway.

**One fixture manifest, not four vocabularies.** "Corpus", "matrix",
"extension" and "expected node type" are used without enumeration, and it is
unclear whether the corpus is the 23 characterisation files, the parity
fixtures, or something new. Build ONE typed manifest with stable IDs, content
classes, per-mode expectations, expected deltas and position expectations, and
derive every matrix from it. WI-3.3's parser-flavour fixtures (frontmatter,
details, block math, alerts, TOC) fold in here as content classes; its action
sweep moved to the design doc.

**Inherited from Phase 1:** the position domain is `canonicalEditorText`. CRLF
belongs to WI-1.9, which exercises it through the real ingress — not to this
gate, which would only measure harness skew.
